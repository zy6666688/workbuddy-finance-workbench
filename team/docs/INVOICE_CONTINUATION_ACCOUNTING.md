# 批次续办、回录台账与记账草稿

开发状态：已完成隔离 PostgreSQL 迁移及自动验收、WorkBuddy 适配器链路和网页桌面／390px 检查，详见 [本轮体检记录](WORKFLOW_HEALTH_REVIEW.md)。正式环境未迁移、未安装或部署；本轮未操作真实 WorkBuddy 桌面会话。

## 员工操作链

1. 打开「批量开票申请」，查看按待办分组的客户项目。原始失败原因保留，另列最近一次续办结果。选择项目后可以补齐原申请、补办原失败项、登记台账或准备记账草稿；筛选不会自动取消已经选中的项目。
2. 补齐某项时先暂存本项内容，再统一提交所选项目。已有申请修订原记录并重新等待独立核验；未保存项补办前查重，发现同工作单已有同业务申请时只关联原记录，不覆盖本次修正内容。跨工作单同业务冲突返回待核实。
3. 上传新原始资料仍使用月度工作单资料入口，会改变该单输入版本。上传后刷新批次待办，明确选择需要修订的项目；程序不会静默刷新其他申请的输入版本。
4. 实际开票失败、结果不明或回录待核验的项目不能作为“申请保存失败”重新创建或撤回。核实原渠道记录后，在原申请继续回录实际结果。本系统不调用开票平台。
5. 独立核验通过的成功回执可以登记唯一销项台账；再次登记返回原台账。历史回执按原核验快照保存，后续业务补件不会改写它。
6. 在月度工作单开票区的「客户可复用记账规则」中，从本期已保存科目表选择科目，填写明确业务类型、条件、期限、必需依据和按净额/税额/价税合计取数的借贷模板。规则需另一名人员核验。新版本核验后立即替代同业务旧版本；未来生效或已经截止的替代规则不会提前或延后适用。
7. 准备草稿时明确处理日期、币种、业务范围、是否已入账和实际确认依据。未入账业务须读取有效规则，并确认具体 `ruleId`、`ruleVersion` 的条件；确认不会自动沿用到新版规则。原始材料按规则要求逐项对应，同一文件可以证明多项要求。
8. 缺少科目表、固定档案、有效规则或依据时保存为「待补资料」。当前只准备本期、明确 CNY、普通蓝字销项业务的草稿。这里“普通业务”不代表根据发票名称判断税种或收入确认时点；开票本身不能替代业务确认。
9. 已入账只关联本期非结转凭证，且本期底稿必须有票号、金额和凭证关联均一致的蓝字销项记录。首期只支持该凭证的借贷合计等于本张发票价税合计；多票合并、拆分或复杂调整挂起。不能通过再次准备草稿重复生成已核验成果。
10. 未参与经办的人员在工作台复核草稿。通过后可下载 XLSX 和 JSON 交接成果；驳回保留历史，修订形成新版本。没有任何正式过账或写入现有核对底稿的动作。

## 状态含义

| 状态 | 下一步 |
| --- | --- |
| 申请待补资料／失败项可补办 | 明确补件，按原项目续办 |
| 申请待核验 | 由独立人员核验申请 |
| 待实际回执／回录待核验 | 回录已有真实结果，或由人员核验回执 |
| 实际开票失败／结果不明 | 核实原渠道，不重新创建申请或自动重开 |
| 账务待补件 | 补科目来源、规则、业务判断或依据 |
| 草稿待复核 | 独立人员复核；依据变化先修订 |
| 交接成果已形成 | 可下载；`posted=false`，未过账 |

续办回执中 `completed` 只表示该项操作已执行。账务操作仍可能生成带缺项的 `blocked` 草稿，须继续读取 `payload.outcome.state/issues`。`blocked` 尝试表示本次操作被拒绝，原成功记录不会被删除。

### 一句话续办到交接的衔接

1. WorkBuddy 查询 actions：每项 `feedback` 汇总申请、授权和账务缺项；`nextStep` 固定工作单、待核验对象及下一步，不能自行扩展所选范围。
2. 只对用户明确选中且依据具备的项目续办。回执返回 `progressQuery`；操作保存后重新查询当前 actions，而不是把历史回执当实时状态。上传补件后先刷新预期版本。
3. `requiresHumanReview=true` 时，向用户说明对应工作单及申请／实际回录／草稿，由独立人员在网页核验。规则生效后可在账务表单刷新规则，重新确认具体版本及适用条件。
4. 账务草稿的缺项直接显示在批次页；编辑期间保留打开时的版本，刷新不能替换提交的预期版本。复核或续办保存后若刷新失败，页面明确区分“已保存”和“进度刷新失败”。
5. `handoff` 仅对已独立核验的成果返回下载入口。下载先核验响应格式，文件完整写入后才以不覆盖方式保存到授权目录；回执返回草稿编号、格式、绝对路径、字节数与摘要。下载不向原始资料目录重新上传、不正式入账。

网络中断或无法解析提交回执时，WorkBuddy 返回 `outcomeUnknown=true`；查询原任务或原样重试，不换 key 重建。内嵌计算及 WorkBuddy 成果回传接口同时返回当前 `progress`：仍有异常、待送审、待复核与已归档分别报告，`ok=true` 仅表示本次回传操作成功。

### 超时、补件与驳回后的恢复

- 网页续办在取得明确回执前保留本次请求原文和 key，并提供“原样重试上次提交”。此时锁定本表单，刷新批次不会替换原请求参数。明确失败项保留填写；成功项退出本次选择，避免一起重办。
- “补件后更新版本，保留填写”只在申请、草稿版本未更换且操作仍允许时，显式更新工作单及尝试版本。申请、草稿或权限冲突保留原输入并提示核实，不静默覆盖。重新打开已暂存的补件编辑器，会带回暂存内容与说明。
- 已提交并留存的失败尝试通过 actions 的 `resume` 返回原 changes/context/reason；`canPrefill=true` 可继续填写，false 只供与当前版本对照。该恢复依赖现有权限及尝试记录，不扩大客户范围。尚未提交的表单和未取得回执的原请求仅保存在当前页面内存，不宣称浏览器关闭后仍能恢复；服务端已保存的尝试可重新查询。
- 回录驳回的核验理由从原审计记录读取，批次明确标记待修正。网页“沿用资料修正回录”带回原回录字段、附件和授权引用，核实后另存新草稿，保留原记录。此明确新尝试使用新 key，避免被当作原已驳回请求重放；超时重试仍用原 key。
- 账务草稿的驳回意见直接显示在批次和草稿页，修订沿用原业务信息与依据，仍生成新版本并等待独立复核。凭证、授权失效或已替换的附件仍需核实，不会自动绕过检查。

## WorkBuddy 和接口

- `team_invoice_batch_actions` → `team_continue_invoice_batch` → `team_invoice_continuation`：按批次准备续办并恢复已保存回执；后续动态进度继续查 actions。
- `team_invoice_accounting_context`：读取本期真实科目和凭证目录；不编造科目、币种、期初或政策口径。
- `team_invoice_accounting_rules`、`team_invoice_accounting_rule`：分页读取规则及版本；`team_prepare_invoice_accounting_rule` / `team_revise_invoice_accounting_rule` 只保存待核验版本。
- `team_register_invoice_ledger`、`team_invoice_ledger`、`team_invoice_ledger_entry`：登记及读取台账、草稿版本目录。
- `team_prepare_invoice_accounting` / `team_revise_invoice_accounting` → `team_invoice_accounting_draft` → `team_download_invoice_accounting`：准备、补齐、查询和下载人工复核后的交接成果。下载限制在授权交接目录内，不覆盖文件。
- MCP 不包含规则通过、草稿通过、撤销人工结论、正式过账或外部开票工具。

接口以 `/api/v1` 为前缀：

| 接口 | 用途 |
| --- | --- |
| `GET /invoice-batches/:id/actions` | 逐项待办、当前申请、最近尝试、账务草稿摘要及可执行操作 |
| `POST /invoice-batches/:id/continue` | 提交明确选择的 1–50 项续办 |
| `GET /invoice-continuations/:id` | 读取原始续办回执 |
| `GET /companies/:id/invoice-accounting-context?period=YYYY-MM` | 本期科目和档案来源 |
| `GET/POST /companies/:id/invoice-accounting-rules` | 分页查询／准备规则版本 |
| `GET /invoice-accounting-rules/:id`、`POST .../revise` | 规则详情和修订 |
| `POST /invoice-requests/:id/ledger` | 按申请版本登记唯一台账 |
| `GET /orders/:id/invoice-ledger`、`GET /invoice-ledger/:id` | 台账与草稿版本目录 |
| `POST /invoice-ledger/:id/accounting-drafts` | 新建或修订最新记账草稿 |
| `GET /invoice-accounting-drafts/:id`、`POST .../revise` | 草稿详情及显式修订 |
| `GET /invoice-accounting-drafts/:id/export?format=xlsx\|json` | 下载已独立复核交接成果 |

规则和草稿的网页 `verify/reject` 接口要求原版本和说明；草稿还沿用工作单的独立复核人员及经办参与者限制。

独立复核同时检查规则本轮的全部编制／修订人员，不能通过换人提交最新版本让前一经办自审。上一个已通过独立核验的版本作为修订链边界，已驳回版本不清除参与记录。规则编制者也不能复核使用该规则生成的账务草稿，即使应用于其他月份；客户端显示原因，服务端同样拦截。

### 续办参数与恢复

每项提交 `itemId,expectedAttemptId,orderVersion,action,reason`。`expectedAttemptId` 来自 actions 的 `expected.attemptId`，首次为 null。

- `repair`：增加 `requestVersion` 和完整 `changes:{payload,sourceFileIds,authorization}`，使用原业务编号。
- `retry`：增加完整 changes，服务端保持原业务编号并查重。
- `ledger`：增加 requestVersion，只接受已独立核验的成功回执。
- `accounting`：增加 requestVersion、draftVersion（首次 0）和 context；同一次操作登记台账并准备草稿。

context 包含业务类型、处理日期、币种、业务范围、处理决定（新增／关联已入账／挂起）、确认依据、说明和附件对应关系。新增分录时还必须明确已经阅读并核实的规则编号、版本和适用条件；不能仅提交“已确认”布尔值代替具体版本。

所有续办携带稳定 key；同 key 的内容必须完全相同。超时原样重试返回原续办回执。改正失败项先刷新 actions，再使用新 key。原单多张发票按本次提交前的工作单版本检查，不受本次前一项自身保存影响。客户端不自动覆盖预期版本来强行重试。

回执固定本次选择的项目数量，查询和重试仍按当前客户权限过滤明细。`totalItems` 是原选择数，`visibleItems` 是当前可见数，`scopeComplete=false` 明确表示结果不完整；不会返回不可访问客户的名称、申请或修正内容。网页和 WorkBuddy 均不得将可见项目的完成情况解释成整批完成。

业务失败按项回滚并留痕；技术故障整体回滚。包含越权或不属于该批次的项目时整单拒绝。尝试列表展示最近 30 次，原记录永久保存在当前业务库历史中（此处不声明法定保管期限）。当前补办链只关联原批次项，不推断此前手工新建批次的父子关系。

数据库唯一性冲突仅将已知的业务编号重复／凭证重复关联作为业务失败；其他完整性错误必须整批回滚，不能吞成某一项失败后提交剩余记录。

## 数据及兼容

新增迁移 `019_invoice_continuation.sql`，不重写 018。增加续办请求／逐项尝试、独立发票台账、客户规则版本、记账草稿版本；全部按组织及客户权限隔离。没有迁移时自动回填台账、草稿或记账规则。

草稿固定当前输入版本、科目底稿、档案、规则和附件摘要。旧规则使用的科目名称或类别发生变化时，先修订核验规则；草稿编制后任何相关依据改变均须重新核实。已核验历史成果按原快照保留，导出注明当前依据是否变化，不将其解释为新一次核验或过账。

原始凭证和业务附件不复制成新的“原始输入”来触发账务任务。仅触碰业务记录版本及经办贡献者，不调用 `invalidateInputs`、不写 `accounting_snapshots`，不会因为准备账务草稿而使原开票依据失效。

## 持续验收清单

以下为完整验收范围；本轮实际执行结果以体检记录为准，未覆盖项不能据此标记通过。

- 多客户、同单多张、混合补件/补办/账务操作；成功、业务失败及技术回滚均准确留痕。
- 重复请求、并发续办、超时恢复、同业务已存在、跨工作单冲突及权限撤销。
- 新资料导致版本变化，仅选中申请被修订；实际失败/不明回录不能借补办重复申请。
- 已核验成功回执重复登记只得一份台账；其他回录状态均拒绝。
- 缺科目/档案/规则/依据、旧条件确认引用新版规则、科目名称类别变化、规则日期不匹配、借贷不平。
- 既有凭证关联缺失、金额不一致、合并凭证或重复关联；均不重复生成分录。
- 经办不能自审，驳回及修订历史保留，复核与并发改资料不产生旧版本通过。
- 规则未经复核时更换提交人、驳回后换人修订、规则跨月应用，均不能绕过参与者限制；已通过的上一版本形成修订链边界。
- 权限撤销后查询或原样重试续办回执，仅返回可见明细并明确标示不完整；未知唯一性冲突引起整个续办事务回滚。
- XLSX/JSON 下载权限、完整来源、授权目录约束、拒绝覆盖文件；导出不写正式账务底稿。
- 网页桌面和窄屏、批次筛选后选中项、补件暂存、逐项错误、历史草稿读取，以及真实 WorkBuddy 桌面工具链。
- 保存成功但刷新失败、提交超时／响应无法解析、编辑期间刷新版本、核验后刷新规则与重新确认条件。
- 成果格式不符、下载中断、目标文件已存在，以及回传响应与后续人工阶段一致性。
- 超时期间刷新后原样重试；部分失败保留输入；补件只更新工作单版本；其他人修订申请／草稿时拒绝套用旧输入；暂存补件重新打开；回录和账务驳回后沿用资料、修正、新 key 保存与旧 key 重放区分。
