# 开票自动化公开资料调研与接入建议

核实日期：2026-10-28（America/New_York）。本次仅查询公开资料，未登录税务局或厂商账户、联系第三方、逆向产品或抓取内部接口，未开展开票测试。来源发布日期单列；未标日期的网页不能据抓取时间认定为新版接口。

## 结论与当前选型

自动开票存在正式接入路径，但“企业微信内嵌网页”和“工作台已有工作流”都不等于已经获得税务局后台调用资格。建议先把现有工作流串成：**业务资料 → 开票申请草稿 → 授权人员确认 → 已签约渠道提交 → 查询/回调 → 发票与附件回写 → 账务草稿与人工复核**。开票、收票、记账、纳税申报应分别表达状态与权限。

当前业务前提是**代账公司服务多个独立客户，逐户取得授权**。本项目不将乐企直连作为默认或当前实施方向，也不把集团企业自用条件类推给代账公司。流程和技术适配封装在自己的工作台后端，WorkBuddy 只调用本工作台已有能力，不额外挂装商业开票插件或商业 MCP。当前先做逐户授权台账、分客户批量准备、导入与结果回录；如现有代账软件或正式服务商允许多客户普通 API 对接，再增加后端适配。未选择供应商、采购或接受付费服务。**白居E仅作为竞品参考，用户没有要求接入该厂商。**

全国数电票已于 2024-12-01 正式推广，包含平台交付及查询下载机制；这不代表所有软件都能直接连接税务局。[国家税务总局公告 2024 年第 11 号](https://fgk.chinatax.gov.cn/zcfgk/c100012/c5236067/content.html)

## 给下一步代码的最小契约

以下是本项目工程建议，不是对任何厂商已开放接口的断言。先将渠道调用包在独立适配层，正式地址、权限与字段以签约文件为准。

1. **申请与审阅**：保存客户/销售方主体、原始业务依据、购方、票种、商品税收分类、金额与税额、附件引用及数据版本。WorkBuddy 可建草稿、补资料、查询进度；只有有权限的人员可确认最终内容。确认后数据变化应重新复核。
2. **提交与去重**：本地申请号与销售方绑定，提交前持久化发送记录；另存渠道申请号、受理号、版本。未知结果/超时进入“结果待确认”，先查后决定是否重试，不能自动换单号再次开票。只有厂商契约明确允许时才能自动重发。
3. **状态分离**：至少区分草稿、待复核、待身份认证、可提交、已受理/开具中、结果未知、开具成功、明确失败、红字待确认、红冲完成。接口调用成功或文件导出成功都不等于发票开具成功。
4. **回执与资料库**：轮询和回调应合并到同一状态更新逻辑；回调验签、防重放并验证租户和销售方。记录票号、开具时间、渠道结果及可用原始文件，下载文件后保留来源和校验值。不能因过期下载链接丢掉已归档附件。
5. **红字与后续账务**：红字申请独立关联原蓝票，区分是否需要对方确认，不把红冲当本地取消。开票结果进入账务工作流后只生成草稿/复核任务，不自动降低入账、付款或纳税申报复核要求。

在取得正式接口前，可完成上述数据结构、现有工作流关联、审批、任务查询、模板导出与人工回录。缺少渠道能力时应返回“未配置/待接入”，保留申请草稿；不伪造受理号或成功票号。

## 可直接咨询的问题（本次未发送）

**给候选厂商（白居E相关问题仅在将其纳入候选时适用）：**

1. 我们使用企业微信内的白居E，请确认完整产品名、版本、签约主体；是否提供当前数电票开放 API、合作伙伴接口或官方导入导出方案？请给版本化文档和适用地区。
2. 我们为多个无股权关联客户服务，各客户如何授权？底层是乐企自用、联用、他用还是其他正式渠道？直连单位是谁，是否允许我们自建工作台调用？
3. 是否能分开“创建开票申请、人员确认、正式提交”？需要谁扫码/刷脸，何时失效，系统能否返回待认证状态及恢复方式？
4. 同一销售方同一订单重复请求如何处理？网络超时但可能已开票时，用哪个字段查询？未知结果能否禁止再次提交？
5. 是否支持查询、回调、发票原始文件获取、红字确认单和部分红冲？回调如何验签，各状态怎样解释？
6. 是否有测试环境、虚构数据测试方式、费用和调用限额？生产入口如何取得？可以先只开通申请/查询能力吗？

**给客户所在地主管税务机关/12366：**

1. 我们为多个独立纳税主体提供代账服务，本地代理业务入口如何建立、核验和解除逐户委托关系？开票是否在委托范围内？
2. 现有代账软件或正式开票服务商接入时，每个客户分别需要完成哪些授权，是否有代理登录的专门要求和技术支持渠道？
3. 每个客户的法人/财务负责人/开票员分别需要做哪些授权，是否跨省支持，授权到期及人员变动如何处理？
4. 数电票批量开具的当前模板、身份认证要求、红字确认流程和异常处理指引在哪里获取？

### 选择建议及可直接复用的设计

1. **将 WorkBuddy 市场里的云帐房应用用于交互对标。**按用户最新要求，本工作台优先自行封装流程与正式接口，不默认安装该应用或调用其商业 MCP，也不要求用户改用白居E。
2. **工作台继续保留自己的流程与台账。**WorkBuddy 发起任务，工作台保存申请及审批，获准渠道执行，回执再回到工作台；不能因第三方对话显示完成，就自动认定本地入账完成。
3. **可学习而无需复制的机制**：先校验销方与授权；用稳定申请号关联渠道任务号；认证/确认阶段暂停等待；查询结果驱动后续步骤；文件上传与开票提交分别记录；批量能力按渠道明确声明，不把连续调用单票接口自动包装成受支持的批量开票。
4. **本轮未找到同时满足“完整开源税局开具后端、许可证明确、当前多省可用、维护与安全证据充分”的 GitHub 项目。**发现的实质路径仍是有授权的商业服务/MCP/API，或具备准入资格的乐企接入；PDF 账单生成、已开发票回传和教学 RPA 都不能替代它。

本轮未为任何候选提供真实资料或凭据，也没有安装市场插件、申请账户、连接税局或执行开票。后续只需围绕选定渠道补齐正式授权和契约，不必为竞品单独开发适配器。

### 自有后端可以先写的代码

建议由既有工作流调用工作台内部 `InvoiceService`，再由可替换的 `TaxChannelAdapter` 处理渠道差异；这是本项目自己的设计名称，不是税局接口名。前端、WorkBuddy 和各工作流不直接拼接税局或厂商请求。

- **业务核心**：申请和原始交易依据、销方与客户绑定、含税/不含税金额及精度校验、商品税收分类候选、复核签名和数据版本、批次/单票关系。
- **稳定内部动作**：`checkReadiness`、`prepare`、`submit`、`query`、`fetchFiles`、`requestRed`。每个渠道单独声明可用票种、批量/红字/查询能力；尚无契约时仅返回未接入，不执行真实提交。
- **状态与去重**：本地申请号在发送前入库，关联渠道请求号；提交前审核数据摘要必须仍匹配。超时进入结果未知，走查询与人工核对；供应商没有明确幂等保证时禁止盲目重发。
- **异步处理**：提交和轮询分离，记录等待认证/确认/补件原因；明确失败与尚未查到结果分离。取消本地任务不等于撤销税局已受理业务。
- **回执与资料库**：核对回执销方、申请、票号和金额；对重复回调去重；查询确认后再推动账务草稿。文件从已核验的渠道地址获取，保留原始 XML/OFD/PDF、来源、校验值和访问权限。
- **配置隔离**：按组织/销售方隔离凭据与授权有效期，凭据不进入提示词、仓库和普通日志；测试与生产环境分开，启用证书校验。正式接口、请求签名、回调认证和税局状态映射在取得对应版本契约后实现。

先完成这些代码，并按逐户授权组织客户数据，后续是否增加路线 B 的普通 API 适配由实际能力和用户选择决定；不为乐企直连预设当前实施计划，也不用为获得商业 MCP 而重做工作流。

### 仍需取得的五项资料

1. **独立客户范围与地区**：客户名单及各自所在地、现有开票软件、已授权人员及代账委托范围；不以集团组织树代替独立客户关系。
2. **逐户授权方式**：代理业务入口、客户确认、开票权限、开票员身份、授权有效期及解除机制，必须与实际渠道要求一致。
3. **版本化技术包**：如选择普通 API，索取允许代账多客户调用的明确说明、当前接口文档、测试环境、租户/销方隔离、查询回写和文件下载契约。不能用“支持多组织”推定“允许代账多主体”。
4. **可验证的恢复约定**：重复提交、网络超时、查无记录、授权过期、风险阻断、红字等待对方确认各自如何处理，何时允许重试。
5. **验收凭证**：区分虚构数据的测试回执与正式开票回执，定义税局可查、票面一致、附件可下载及账务草稿关联的验收证据。当前用户要求先代码，本轮不申请环境或执行真实开票。

本节结论：**围绕代账公司逐户授权，把客户台账、申请审核、批量准备、状态跟踪和归档集中在自己的程序中。**当前不推进乐企直连；正式开票适配以现有代账软件/服务商实际开放的普通 API 或已获授权的导入方式为准，不猜测隐藏接口。

## 最终修正：按代账公司逐户授权评估

### 本项目现在采用的顺序

1. **逐户登记授权**：客户 ID、销售方税号、地区、现有开票渠道、委托范围、授权人员、确认凭证、有效期、是否可开票/查询/红冲分别保存。工作台权限、软件 API 授权、税局办税身份是不同层次，不能合并成一个“已登录”。
2. **批量准备，逐户隔离**：工作台接收一份总清单，按销售方拆成独立任务；每户校验和复核后导出对应模板。所谓批次是本地编排，不能在未确认渠道能力时宣称跨客户批量开具。
3. **使用当前有授权的办理方式**：已获准的导入/人工办理先接回录；仅在拿到明确允许代账多客户调用的普通 API 契约后，将提交/查询/文件获取封装进自己的后端。无需外挂商业 MCP。
4. **结果与失效处理**：按客户、销售方税号、申请流水号关联回执，回写资料库及账务草稿；认证过期只暂停该客户，保留待办并引导相应人员处理。超时不能直接改成失败再开一次。

后续候选核验只需问清四件事：**是否允许代账机构服务独立客户；每个客户如何授权和撤销；单票/同户批量/跨户批量各自支持什么；怎样查询结果、取得附件并识别授权失效。**未提供对应契约的候选保留“待确认”，不安装、不收费开通、不替用户选供应商。
