# 工作台与 WorkBuddy 流程体检

检查日期：2026-10-29。范围为当前累计开发源码中的客户档案、工作流、批量开票申请续办、规则与记账草稿、人工复核及交接成果。按用户本轮要求恢复自动检查和隔离测试，准备 PR；没有部署或修改正式账号、数据库、附件及已安装 WorkBuddy。

## 本轮发现及修复

- 续办接口的联合类型含默认值，原 JSON Schema 校验器在注册路由时失败，导致服务无法启动。共享 POST 入口改为使用 Zod 校验输入并应用默认值，保留严格字段和业务条件校验；生成输入口径的 API 文档。增加无需数据库即可执行的全部路由启动回归检查。
- 回录状态与驳回原因查询将审计目标 text 与申请 UUID 直接比较，实际 PostgreSQL 报错。两处查询均显式转换类型，实际回录、驳回、列表及续办待办链路已覆盖。
- 续办重试后权限发生变化时，网页过去会清除没有返回结果的已选项。现在只清除明确完成项，保留无法确认项的资料，并显示回执不完整提示。服务端重放继续按当前客户权限过滤，不扩大范围。
- 批次列表将保留的初始失败数量写成“未保存”，容易被误解为补办后的状态。现注明“初始未保存”，当前状态见逐户进度。
- 离线复刻包的源码摘要未同步，已按最终源码重新生成。
- 根项目锁文件中间接依赖 `@hono/node-server` 升至兼容修复版本 2.1.5，消除本轮审计发现的中危告警；未批量升级依赖。
- PR 的远端完整交付演练进一步发现后台队列积压：标准队列的 `send(singletonKey)` 不会合并等待记录，且批量处理中的一项异常会跳过其他已取出的项。改为按业务任务 key 执行 `upsert`，只保留一条等待调度记录，并逐项消费、独立结算失败。随后在新的隔离 Docker 环境重跑全部 79 项检查及真实 Worker 的资料交付演练通过；包含补件、下载任务包、回传、驳回更正、独立复核、交付归档及重开历史保护。
- 备份恢复演练发现两组测试样本只有附件记录、没有对应文件，现同步写入虚构文件及真实摘要；恢复比对增加续办、回录、台账、规则版本、记账草稿和账务快照，避免新功能被恢复检查遗漏。

## 本轮新增自动回归覆盖

- 保存失败的修正内容持久保留；原请求重放、并发同请求只产生一份结果；相同 key 改内容拒绝。
- 补件只修订选中的原申请，未选申请仍显示依据变化；原申请编号和历史保留。
- 回录驳回意见可查询；复制原回录字段、附件和授权修正另存，再次独立核验；成功回录台账只登记一份。
- 缺少科目底稿时草稿挂起，不猜科目；已填写确认依据保留。
- 规则独立核验、新版本生效导致旧草稿失效；更新规则引用后生成新草稿并复核。
- 账务驳回后沿用原 context 与附件补充说明；经办无法自审；XLSX／JSON 仅在复核通过后导出，不修改账务底稿。
- WorkBuddy 共享客户端／适配器实际调用同一 API 服务，查询待办并将已核验成果写入授权临时目录，返回路径、字节数、摘要和未过账标记；既有文件不覆盖，临时文件不残留。
- 传输超时、无效响应、服务错误不自动新建请求；明确重试保持相同 key 和完整内容；错误页面与中断下载不被报告为成功。
- 已有同业务申请补办时关联原申请；注入数据库技术故障后整次续办回滚。
- 跨机构、客户撤权后不可读取草稿与回录；原操作重放只返回仍可访问的明细，并标示回执不完整。
