# 一句话任务与自动开票竞品调研

核实日期：2026-10-28。白居E（企微内嵌网页）是用户提供的竞品线索，不是指定接入平台。当前开发优先完成工作台内嵌工作流、WorkBuddy 账务串联及平台无关的开票申请/进度管理。第三方接入另作能力评估；不做逆向开发。

## 产品现状与差距

本工作台已有客户档案、月度工作单、附件版本、工作流任务包、成果回传、独立复核、交付证据及归档。底稿核对不能等同正式账务系统或真实开票系统。

| 对标方向 | 成熟产品公开能力 | 本次结论 |
|---|---|---|
| 工作流衔接 | 业务系统到发票平台的申请、开具、结果查询形成连续流程 | 先合并本工作台任务创建和打包，增加按任务编号查询；减少中途断开和重复创建 |
| 开票 | 金蝶发票云公开介绍第三方系统 API 集成；百望开放平台列出直开和预制发票模式 | 本工作台尚无已验收的开票连接器，不能承诺一句话直接开出真实票 |
| 账票衔接 | 金蝶云会计公开介绍票据处理及凭证等功能 | 当前财务底稿应继续明确“核对、待复核”，后续需完成正式账套映射和可追溯凭证接口 |
| 自动化持续运行 | 连续任务需要执行者、错误恢复和结果记录 | 本次提供持久状态及资料打包；模型处理仍发生在 WorkBuddy 活跃会话中，未新增无人值守模型执行器 |

## 推荐落地顺序

第一步：WorkBuddy 从已授权客户资料及真实业务依据整理开票申请，生成待核验明细和缺项清单。销方、购方、税号、业务依据、商品、数量、单位、含税口径、金额、税率和税收分类编码逐项记录来源。没有依据的值保持缺项，禁止凭商品名称自行决定税率。

第二步：评估候选渠道当前版本的官方导入模板、API 或 WorkBuddy 应用，选定后再核实授权和契约。若支持清单导入，按真实模板生成文件，由开票员在现有系统确认并开具；若提供官方 API，完成测试环境授权、申请提交和结果查询后再启用对接。尚未拿到模板前不生成伪装成“可直接导入”的文件。

第三步：把开票平台的申请编号、处理状态、发票号码、开票时间及原始电子文件回写到对应客户和业务申请，按发票唯一标识去重。超时先查询原申请；状态不明时显示“结果待确认”，不重新开一张。回调与主动查询需校验授权、去重并保持可追溯。

申请状态建议：草稿 → 缺项/待复核 → 已确认 → 已提交 → 开具中 → 已开具/失败/结果待确认 → 已归档。红字作为关联原票的新流程，需单独设计授权和确认，不用删除原记录代替。

角色：WorkBuddy 准备资料；经办核验业务依据；授权开票员确认并开具；复核人员核对结果。记录每次状态变化的操作人、公司、申请编号、输入版本、原因、时间和平台结果。凭据只放部署配置，客户税号和账户不写进代码或公开日志。

接入前需要厂商明确：当前版本是否支持开放 API 或商品/订单导入；正式模板及字段；企业与开票员授权方式；测试环境；申请幂等标识；结果查询与回调；电子文件下载；超时、重复申请及红字处理方式。当前未联系厂商、未提交申请、未开具发票。

验收至少覆盖：客户隔离、缺项阻断、重复申请、金额分位与合计、确认前数据变更、超时后成功、重复回调、部分批次失败、授权撤销、原票与红字关联、原件下载及归档。未拿到厂商契约之前，这些是接入要求，不是已实现功能。
